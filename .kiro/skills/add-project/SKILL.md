# 프로젝트 추가 (add-project)

새 프로젝트를 이 포트폴리오의 기존 규격에 맞춰 추가한다.
`/add-project <프로젝트 이름>` 처럼 이름이나 자료를 뒤에 붙여 호출하면 그 내용을 출발점으로 쓴다.

## 지켜야 할 원칙

1. **사실은 사용자가 준 것만 쓴다.** 수치, 기간, 회사, 역할, 성과를 지어내거나 추정하지 않는다. 모르면 비워 두고 사용자에게 묻는다.
2. **초안은 만들되 확정은 사용자가 한다.** 사용자가 준 자료(README, 노션 글, 이력서 문장, 대화)로 문장을 다듬어 초안을 보여 주고, 확인을 받은 뒤 파일에 쓴다.
3. 기존 프로젝트 데이터(`market-insight`, `sellfit-ai`, `pds`, `hospital-reservation`)의 문체와 구조를 따른다.
4. `.kiro/steering/rules.md`와 `structure.md`를 먼저 읽고 따른다. 특히 **커밋, 푸시, PR은 사용자가 요청할 때만** 한다.
5. 사내 기밀이 될 수 있는 내용(고객사 이름, 내부 URL, 키, 개인정보가 보이는 화면)이 있는지 확인하고, 있으면 가리거나 빼도록 안내한다.

## 작업 순서

### 0. 준비

- `.kiro/steering/rules.md`, `.kiro/steering/structure.md`를 읽는다.
- `git status`와 현재 브랜치를 확인한다. `main`이면 `feat/add-project-<slug>` 브랜치를 만든다. 슬러그가 정해지기 전이라면 2단계 이후에 만든다. 커밋하지는 않는다.
- 이미 있는 프로젝트 목록과 `order`를 확인한다: `src/entities/project/api/project.repository.ts`, `src/entities/project/api/data/*.ts`.

### 1. 정보 수집

`references/intake-checklist.md`의 질문 목록으로 사용자에게 필요한 정보를 요청한다.

- 한 번에 모두 묻지 말고 **필수 정보 → 화면 자료 → 케이스 스터디 내용 → 선택 정보** 순서로 묶어서 묻는다.
- 사용자가 자료를 통째로 붙여 넣으면, 질문하기 전에 그 안에서 채울 수 있는 항목을 먼저 채우고 **빠진 것만** 묻는다.
- 정보가 다 모이면 요약표(제목, 기간, 회사, 수치, 스택, 하이라이트 제목, 이미지 목록)를 보여 주고 "이대로 진행할까요?"를 확인한다.

### 2. 슬러그와 순서 결정

- 슬러그: 영문 소문자와 하이픈(예: `my-service`). 사용자가 정하지 않으면 제안하고 확인받는다. URL(`/projects/<slug>`)과 이미지 폴더 이름이 된다.
- `order`: 목록 노출 순서(1부터). 사용자에게 몇 번째에 둘지 묻는다. 기본 제안은 **맨 뒤**다.
  - 중간에 끼워 넣으면 기존 프로젝트의 `order`를 한 칸씩 밀어야 한다. 기존 파일을 수정하므로 변경 내용을 알리고 확인받는다.

### 3. 이미지·영상 처리

`references/assets.md`의 규격과 명령어를 따른다.

- 사용자가 준 원본 경로를 읽어 `public/images/projects/<슬러그>/`에 **변환본만** 만든다. 원본은 수정·삭제하지 않고, 원본 PNG/GIF를 `public/`에 복사하지 않는다.
- 변환 후 실제 가로·세로 픽셀을 측정해 데이터 파일의 `width`, `height`에 쓴다. 추측하지 않는다.
- `alt`와 `caption`은 화면을 직접 보고 쓴 한국어 문장으로 작성하고, 사용자에게 확인받는다.
- 이미지가 없는 프로젝트도 허용된다(`cover` 생략 시 점 격자 패턴이 표시됨). 다만 사용자에게 한 번 알린다.

### 4. 데이터 파일 작성

`references/data-template.md`의 템플릿과 문체 규칙으로 `src/entities/project/api/data/<슬러그>.ts`를 만든다.

- 파일명은 슬러그와 같은 kebab-case, export 이름은 camelCase(`my-service` → `myService`).
- `Project` 타입(`src/entities/project/model/types.ts`)을 만족해야 한다. 타입 에러가 나면 데이터를 고치고, 타입을 임의로 바꾸지 않는다.
- 파일 상단과 export에 한국어 JSDoc(`@alias`, `@description`)을 단다.

### 5. 등록 (메인 화면 반영)

아래 두 곳만 수정하면 메인 화면, 상세 페이지, 사이트맵이 자동으로 갱신된다.

1. `src/entities/project/model/types.ts`: `ProjectSlug` 유니온에 새 슬러그를 추가한다.
2. `src/entities/project/api/project.repository.ts`: 데이터 파일을 import 하고 `PROJECTS` 배열에 추가한다. (`order`로 정렬되므로 배열 위치는 상관없다.)

자동으로 반영되는 곳(수정하지 않는다):

| 화면 | 반영 방식 |
| --- | --- |
| 메인 `#projects` 카드 목록 | `getProjects()` → `ProjectShowcase` |
| 히어로의 "대표 프로젝트" 개수 | `projects.length` |
| 히어로의 대표 프로젝트 이미지 | `cover`가 있는 프로젝트 중 앞의 2개 |
| 히어로의 수치 카드 | `featured: true`인 수치 중 앞의 3개 |
| 상세 페이지 `/projects/<slug>` | `generateStaticParams`, `generateMetadata` |
| 상세 페이지 이전/다음 링크 | `getAdjacentProjects()` |
| `sitemap.xml` | `getProjectSlugs()` |

수동으로 확인할 곳:

- **히어로 수치 카드**: `featured: true` 수치가 전체 프로젝트 합쳐 3개를 넘으면 앞의 3개만 보인다. 새 수치를 featured로 두면 기존 수치가 밀려날 수 있으니 사용자에게 알리고 정한다.
- **기술 스택 섹션**(`src/entities/skill/api/skill.repository.ts`): 새 프로젝트의 `stack`에 이 목록에 없는 기술이 있으면 사용자에게 추가할지 묻는다. 이력서 기준 목록이므로 묻지 않고 추가하지 않는다.
- **하드코딩된 문구**: `grep -rn "프로젝트" src app README.md`로 "프로젝트 N개" 같은 고정 숫자나 목록이 없는지 확인한다.

### 6. 검증

`rules.md`의 자가 검증 루틴을 모두 실행한다. 새 라우트가 생기므로 빌드까지 필요하다.

```bash
npm run lint
npm run typecheck
npm run build
```

- 빌드 출력에 `/projects/<슬러그>`가 정적 경로로 생성됐는지 확인한다.
- 이미지/영상 경로가 모두 실제 파일로 존재하는지 확인한다(`ls`로 데이터 파일에 적은 `src`, `poster` 전부).
- 가능하면 `npm run dev`로 메인(`/#projects`)과 `/projects/<슬러그>`를 열어 카드, 커버, 하이라이트, 이전/다음 링크를 확인한다. 확인하지 못했다면 보고에 적는다.

### 7. 보고

짧게 보고한다.

- 만든 파일과 수정한 파일 목록
- 실행한 검증 명령과 결과
- 사용자가 확인해야 할 것(비워 둔 항목, 추정이 들어간 문장, 화면 기밀 여부)
- **커밋하지 않았다**는 사실. 사용자가 커밋을 요청하면 `rules.md` 규칙대로 커밋한다. 예: `feat(project): <제목> 케이스 스터디 추가`

## 저장소·데모 링크 처리

링크는 **없어도 정상**이다. 사내 프로젝트, 비공개 저장소, 이미 내려간 서비스는 링크가 없는 것이 일반적이다.

### 링크가 없는 경우 (기본 흐름)

- 1단계에서 한 번만 가볍게 묻는다: "공개된 저장소나 데모 링크가 있나요? 없거나 비공개면 '없음'이라고 답해 주세요."
- 사용자가 "없음", "비공개", "사내", 또는 무응답이면 **그대로 넘어가고 다시 묻지 않는다.** 설득하거나 이유를 캐묻지 않는다.
- 링크 자리를 채우려고 URL을 추측하거나 만들지 않는다(`github.com/<사용자>/<프로젝트명>` 같은 추정 금지). 빈 문자열, `#`, `TODO`, "준비 중" 같은 자리표시도 데이터에 넣지 않는다.
- 링크가 없다는 이유로 화면 구성이나 문구를 바꾸지 않는다. 케이스 스터디는 링크 없이도 완결되어야 한다.
- 비공개 저장소의 URL, 사내 도메인, 내부 주소는 공개 사이트에 노출하면 안 되므로 사용자가 주더라도 먼저 "공개해도 되는 주소인지" 확인한다. 공개 불가면 기록하지 않는다.
- 링크가 없으면 확인 요약표와 최종 보고에 "링크: 없음"으로만 적는다. 경고나 후속 작업으로 만들지 않는다.

### 링크가 있는 경우

- 현재 `Project` 모델에는 링크 필드가 없다. 사용자가 링크를 주면 "현재 화면에는 표시할 자리가 없다"고 알리고, 아래 중 고르게 한다.
  1. **지금은 표시하지 않기**: 링크는 최종 보고에 남기고 데이터에는 쓰지 않는다.
  2. **모델 확장**: `Project`에 **선택 필드** `links?: readonly { label: string; href: string }[]`를 추가하고 상세 페이지 머리말에 표시한다. 별도 작업이므로 승인받은 뒤에만 하고, 프로젝트 추가와 **다른 커밋 단위**(`feat(project): 프로젝트 링크 표시 추가`)로 다룬다.
- 모델이 이미 확장되어 있으면(`types.ts`에 `links`가 있으면) 링크가 있는 프로젝트에만 `links`를 쓴다. 링크가 없는 프로젝트는 **`links` 필드 자체를 생략**한다. 빈 배열도 쓰지 않는다.
- 확장된 모델에서 UI는 `links`가 없거나 비어 있을 때 링크 영역을 아예 렌더링하지 않아야 한다. 확장 작업 중 이 조건을 지키고, 링크 없는 기존 프로젝트 4개가 이전과 똑같이 보이는지 확인한다.
- 링크 하나당 `label`은 "GitHub", "데모"처럼 짧게 쓰고, `href`는 `https://`로 시작하는 사용자가 준 주소만 쓴다. 외부 링크는 `target="_blank"`와 `rel="noopener noreferrer"`, 그리고 "(새 창에서 열림)" 안내를 단다(히어로의 GitHub 링크와 동일).

## 하지 않는 것

- 새 의존성 설치, 스키마(`types.ts`)의 필드 추가나 변경, UI 컴포넌트 수정. 필요하면 사용자에게 제안하고 확인받는다.
- 승인 없이 링크 표시용 모델·UI 추가. 위의 "저장소·데모 링크 처리"를 따른다.
- 기존 프로젝트의 내용 수정(요청받은 `order` 조정 제외).
- 커밋, 푸시, PR 생성.
