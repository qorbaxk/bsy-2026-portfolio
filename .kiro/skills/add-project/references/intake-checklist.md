# 정보 수집 체크리스트

사용자에게 묻는 항목이다. 이미 받은 정보는 다시 묻지 않는다. 모르겠다고 하면 해당 항목은 비우거나 생략한다.
항목을 한꺼번에 나열하지 말고 단계별로 묶어서 묻는다.

## A. 필수 정보 (이게 있어야 시작)

| 항목 | 데이터 필드 | 설명 / 예시 |
| --- | --- | --- |
| 프로젝트 이름 | `title`, `shortTitle` | 제목과 짧은 표기(내비게이션, 이전/다음 링크용). 예: "PDS (사내 디자인 시스템)" / "PDS" |
| 한 줄 소개 | `headline` | 카드와 상세 상단에 쓰는 한 줄. 예: "공통 UI 패키지의 사용·배포 경계를 다듬은 개발 기록". 없으면 자료를 보고 제안 |
| 소속(회사/팀) | `company` | 예: "커넥트웨이브" |
| 기간 | `period` | `YYYY.MM - YYYY.MM` 또는 `YYYY.MM - 진행 중` |
| 맡은 역할 | `contributions`, `responsibilities` | 대표 역할 3개 이내(제목+짧은 설명)와, 담당 업무 문장 3~6개 |
| 기술 스택 | `stack` | 화면에 표시될 순서대로. 예: React, TypeScript, Storybook |
| 최종 성과 한 문장 | `outcome` | 이력서에 쓰는 성과 문장. 정량 근거가 없으면 정성적으로만 |

## B. 화면 자료 (이미지·영상)

| 항목 | 설명 |
| --- | --- |
| 대표 화면 1장 (`cover`) | 카드와 상세 상단에 쓰인다. 가로형이면 가장 좋다. 카드는 4:3 비율로 **왼쪽 위 기준으로 잘리므로** 제목·사이드바가 왼쪽 위에 보이는 화면이 좋다 |
| 하이라이트별 화면 | 하이라이트마다 0~3장. 파일 경로와 한 줄 설명(무슨 화면인지) |
| 움직이는 화면 | GIF 또는 화면 녹화 파일이 있으면 경로. MP4로 변환한다 |
| 파일 경로 | 로컬 절대 경로(예: `~/Desktop/shots/home.png`) 또는 폴더 경로 |
| 기밀 확인 | 고객 이름, 개인정보, 내부 URL, 키가 화면에 보이면 가려야 한다. 확인 질문: "화면에 외부에 공개하면 안 되는 정보가 있나요?" |

이미지가 아직 없으면 `cover` 없이 진행할 수 있다고 알리고, 나중에 추가할 수 있다고 안내한다.

## C. 케이스 스터디 내용 (하이라이트 1~4개)

하이라이트 하나는 "기술적 문제 한 가지"를 **맥락 → 해결 → 트레이드오프 → 결과** 순서로 설명한다.
사용자가 자료(README, 노션, 회고 글)를 주면 거기서 하이라이트 후보를 뽑아 제안한다. 후보마다 아래를 묻는다.

| 항목 | 데이터 필드 | 필수 | 질문 예시 |
| --- | --- | --- | --- |
| 분야 | `category` | 필수 | "이 이야기를 한두 단어로 부르면?" (예: "스타일 · 테마") |
| 제목 | `title` | 필수 | 문제나 결정이 드러나는 한 문장 |
| 한 줄 맥락 | `lead` | 필수 | "무엇을 왜 바꿨나요?" |
| 문제 상황 | `problem` | 선택 | "기존 방식의 어떤 점이 문제였나요?" |
| 핵심 결정/구현 | `points` (3~5개) | 필수 | "구체적으로 무엇을 했나요?" 제목+설명 |
| 항목 성격 | `pointsStyle` | 필수 | 순서가 있으면 `steps`, 병렬이면 `list`. 사용자에게 묻지 말고 내용으로 판단 |
| 처리 흐름 | `flow` | 선택 | 입력→처리→출력 같은 파이프라인이 있는지 |
| 트레이드오프 | `tradeoff` | 선택 | "이 선택으로 얻은 것과 감수한 것은?" |
| 전후 비교 | `comparison` | 선택 | 전/후 수치. **수치와 기준은 사용자가 준 것만** |
| 결과 한 문장 | `outcome` | 선택 | 하이라이트의 최종 결과 |
| 보충 메모 | `note` | 선택 | 설계 원칙, 참여 범위, 검증 방식 |

수집 팁:

- 하이라이트는 많을수록 좋지 않다. 가장 설명할 이야기가 있는 2~4개를 고른다.
- "측정한 수치가 있나요? 있다면 기준(언제, 무엇과 비교)도 알려 주세요"를 꼭 묻는다.
- 수치에 근거가 약하면 `caption`에 "당시 작업 경험 기준"처럼 기준을 솔직하게 적는다. 기존 `sellfit-ai.ts`가 이 방식이다.

## D. 핵심 수치 (`metrics`)

| 항목 | 설명 |
| --- | --- |
| `value` | 강조할 값. 예: "약 80%", "4개", "1일 → 3분" |
| `label` | 값의 의미. 예: "생성 1회 원가 감소" |
| `caption` | 기준이나 출처(선택). 예: "약 500원 → 약 100원 · 당시 운영 기준" |
| `featured` | 메인 히어로에도 노출할지. 히어로는 전체 프로젝트 중 앞의 3개만 보여준다. 기존 featured 수치와 겹치면 사용자에게 정하게 한다 |

수치가 없으면 `metrics: []`로 두거나 "개수"처럼 사실로 셀 수 있는 값만 쓴다. 숫자를 만들어 내지 않는다.

## E. 선택 정보

| 항목 | 처리 |
| --- | --- |
| 코드 저장소(GitHub 등) URL | **없을 수 있다.** "공개된 저장소나 데모 링크가 있나요? 없거나 비공개면 '없음'이라고 답해 주세요."로 한 번만 묻는다. 없음/비공개/무응답이면 그대로 진행하고 다시 묻지 않는다. 있으면 SKILL.md의 "저장소·데모 링크 처리"를 따른다 |
| 배포된 서비스/데모 URL | 위와 같음. 서비스가 종료됐거나 사내 전용이면 없음으로 처리 |
| 링크의 공개 가능 여부 | 링크를 받았을 때만 확인: 비공개 저장소, 사내 도메인, 내부 주소는 공개 사이트에 쓰지 않는다 |
| 공개 가능 여부 | 사내 프로젝트라면 이름, 화면, 수치를 공개해도 되는지 확인 |
| 목록에서의 위치 | 몇 번째에 둘지. 기본은 맨 뒤 |
| 슬러그 | 영문 소문자+하이픈. 없으면 제안 |
